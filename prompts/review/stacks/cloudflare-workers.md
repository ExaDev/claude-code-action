## Cloudflare Workers

Detected from a `wrangler.jsonc`, `wrangler.json`, or `wrangler.toml`. Where the repository also has a `turbo.json`, a Next.js app deployed through `@opennextjs/cloudflare`, or Drizzle against D1, the corresponding sections below apply.

**The highest-value thing to check is what runs where.** Module scope runs once when an isolate starts, not once per request, and an isolate is reused across many requests. A build step runs on a machine with a full Node.js and the whole workspace on disk; the deployed Worker runs from a bundle, in a runtime implementing only part of Node's API surface. Most real defects here are code that is correct in one of those places and wrong in another.

### Bindings and the request boundary

- Bindings, vars, and secrets come from the handler's `env` parameter (`fetch(request, env, ctx)`) or from `import { env } from "cloudflare:workers"`. A bare global naming a binding is the legacy Service Worker format and does not work in a module Worker.
- `import { env }` reads at module scope, but I/O outside a request context is still forbidden. Reading a var or secret at top level is fine, and so is obtaining a Durable Object stub; calling a KV method, calling through a Service Binding, or calling a method on that stub is not.
- **A client built at module scope keeps whatever it captured for the isolate's whole lifetime.** Nothing in the code bounds that lifetime, so a client constructed once from `env.SOME_SECRET` can keep presenting the pre-rotation value long after the secret changed. Build clients that hold a credential per request.
- A module-level mutable variable holding request-scoped state is a cross-request leak: what one request stored is visible to the next, and I/O attempted against the wrong request's context fails outright. Pass state through arguments.
- An un-awaited promise in a handler can be silently cancelled once the response is returned, with no error surfaced. Every background write, log flush, or cache fill is either awaited or handed to `ctx.waitUntil()`.
- **Bindings are not inherited by named environments.** `vars`, `durable_objects`, `kv_namespaces`, `r2_buckets`, `services`, `queues`, and the other binding keys are non-inheritable: a top-level declaration does not fall through to `env.<name>`, and every environment must declare its own. A binding added only at the top level of a config that has environments breaks the next `--env` deploy, not this one.

### Service Bindings between Workers

- **The binding declaration is the authorisation.** A Worker can only reach one it names in its own `services` config, and the target can be left unreachable from the internet (`workers_dev = false`, no route). That is what makes it defensible for the target to skip an authentication check, so a diff adding a route, a custom domain, or `workers_dev = true` to a Worker whose handlers assume Service-Binding-only ingress is a security finding, not a configuration tidy-up.
- Worker-to-Worker traffic must go through a Service Binding or a custom domain. A plain global `fetch()` to another Worker on the same zone fails.
- Binding to a Worker deployed under a named environment needs the `<worker-name>-<environment-name>` form in `service`. A binding naming the bare Worker from a staging config quietly points staging at production.

### D1 and Drizzle

- **D1 has no interactive transaction.** Nothing holds `BEGIN`/`COMMIT` across calls; `batch()` is the only mechanism that groups statements, and it is a genuine transaction, aborting and rolling back the whole sequence when one statement fails. A multi-step write issued as separate awaited statements has no atomicity whatever, each step committing on its own. This is the first thing to look for in a D1 diff: a loop of individual writes, or two dependent updates in sequence, where the whole thing needed to be one `batch([...])`.
- A batch is one call from one Worker, so a write sequence split across a Service Binding hop cannot be atomic. If a diff moves half a write path into another Worker, ask what state the data is in when the second half fails.
- Drizzle's `db.batch([...])` takes Drizzle query builders, `env.DB.batch()` takes `D1PreparedStatement`s; mixing the two layers is worth catching in review rather than at runtime. Drizzle's cache extension is documented as not working with raw `db.execute` queries or inside transactions, so flag a diff that caches either.
- The driver import must be `drizzle-orm/d1`, constructed from the `D1Database` binding. A `postgres-js`, `node-postgres`, `mysql2`, or `better-sqlite3` import against a D1 binding is an easy copy-paste error in a monorepo holding more than one dialect.
- **Pick one migration applier and stay with it.** `drizzle-kit migrate` records what it applied in its own table (`__drizzle_migrations` by default), `wrangler d1 migrations apply` in D1's `d1_migrations`. Using both against one database double-applies, because neither tracker sees the other's work. Where Wrangler is the applier, check `migrations_dir`, and `migrations_pattern` for Drizzle's nested layout, actually point at the generated files. `drizzle-kit push`, which skips migration files entirely, is a local prototyping tool: pointed at a shared or deployed database it is a finding.
- Foreign keys are enforced by default in D1, unlike vanilla SQLite, and a query cannot turn them off. A migration rewriting or reordering constrained tables needs `PRAGMA defer_foreign_keys`, not an assumption that constraints are inert.
- **There is no native JSON or array column type.** JSON lives in `TEXT` and is read with `json_extract` or `->>`. A predicate over an extracted value cannot use an index the way a Postgres `jsonb` GIN index would, so a new hot query filtering on a JSON property wants a generated column with an index on it, not the extract in the `WHERE` clause.
- Rows read is charged and quota'd by scan cost, not rows returned: a filtered `SELECT` over an unindexed column reads the whole table however few rows come back, and exhausting the Free plan's daily row allowance makes D1 return errors rather than merely bill for it. Each index costs an extra written row per insert or update touching the indexed column, so adding one to a bulk-write path is a trade, not a free win.
- Bound parameters are capped at 100 per query, and queries per Worker invocation at 1000 on Paid but only 50 on Free, so an `IN` clause or a write loop built from a variable-length array needs chunking rather than trust that the array stays short.
- `LIKE` is case-insensitive for ASCII by default, as in SQLite, so a query relying on it to discriminate case is wrong. D1 retries read-only queries automatically but not writes, so an idempotent write whose failure matters needs its own retry.

### Worker size and startup cost

- The limit applies to the **gzip-compressed** bundle: 3 MB on the Free plan, 10 MB on Paid, 64 MB uncompressed on both. An uncompressed byte count is not the number that decides a deploy; `wrangler deploy --outdir bundled/ --dry-run` prints both.
- **Anything imported at module scope in server-rendered code ships in the Worker.** The recurring defect is a browser-only library (a visualisation component, an editor, a multi-provider SDK) imported into a Server Component or server module, contributing its full weight to the server bundle while rendering nothing on the server. Keep the `"use client"` boundary tight and pull such things in with `next/dynamic`, using `{ ssr: false }` where they are genuinely browser-only.
- For an OpenNext build, inspect `.open-next/server-functions/default/handler.mjs.meta.json` with an esbuild bundle analyser rather than guessing which dependency grew. A package shipping several export conditions can have the wrong one picked, pulling in a larger variant; setting `WRANGLER_BUILD_CONDITIONS=""` alongside `WRANGLER_BUILD_PLATFORM="node"` forces Node resolution.
- Startup time, meaning parsing plus executing top-level scope, is capped at one second on both plans, so expensive module-scope initialisation can fail a Worker sitting comfortably under the size limit.

### Next.js on Workers

- `@opennextjs/cloudflare` requires the `nodejs_compat` flag and a `compatibility_date` of `2024-09-23` or later; a new or copied Worker config missing either is broken, not merely unconventional. `global_fetch_strictly_public` is recommended rather than required, so its absence is not itself a defect. `export const runtime = "edge"` is unsupported by this adapter and must be removed.
- **`nodejs_compat` is not Node.** Some `node:` modules are natively implemented and others are polyfills that import cleanly, then throw `"[unenv] ... is not implemented yet!"` or silently no-op when the method is actually called. A build that resolves is not evidence the code path works at request time. Which modules are available also depends on `compatibility_date`, so two Workers in one repository, both with the flag on but with different dates, do not have the same API surface: where a diff moves code between Workers, compare their dates.
- `process.env` is populated from vars and secrets only when `nodejs_compat` is on and the `compatibility_date` is `2025-04-01` or later, or `nodejs_compat_populate_process_env` is set explicitly. Below that date it is empty, so a dependency reading `process.env.FOO` sees nothing while `env.FOO` on the handler works fine: check the date before assuming either behaviour.
- **Caching.** SSR needs no cache configuration; SSG, ISR, and the Data Cache do. Workers KV is explicitly not recommended as the incremental cache because it is eventually consistent, which is a correctness concern for ISR rather than a latency one. On-demand (tag) revalidation needs a tag cache backed by D1 or Durable Objects, and time-based revalidation needs a Durable-Object-backed queue. A diff introducing `revalidateTag`, `revalidatePath`, or a `revalidate` window without the matching backend configured will not behave as written.
- `Cannot perform I/O on behalf of a different request` from a route is a documented symptom of a client, stream, or response cached across requests in module scope, not a fault in the adapter.

### Turborepo tasks and caching

- **`inputs` without the `$TURBO_DEFAULT$` sentinel replaces the defaults rather than extending them.** A narrowed `inputs` list silently stops the task hashing real source changes and serves a stale cached result. The correct form keeps the sentinel and adds to it: `["$TURBO_DEFAULT$", "!README.md"]`.
- `env` lists variable _names_ only and does not read `.env` files, so a task whose behaviour depends on `.env` contents must list those files in `inputs` too or its cache key misses every change to them. `passThroughEnv` is the counterpart, for values needed at runtime but deliberately outside the hash.
- `outputs` is what gets captured and restored, not what gets hashed. A task producing files while declaring no `outputs` restores nothing on a cache hit. A pure check (lint, typecheck) correctly declares `outputs: []`; a Next.js build wants `.next/**` with `.next/cache/**` excluded.
- `^task` means the task in this package's dependencies, bare `task` the same package, `pkg#task` one named package. Confusing the first two is the common `dependsOn` defect, producing either missing ordering or a needless serialisation.
- `globalDependencies`, `globalEnv`, the root `package.json`, and the lockfile are in every task's hash, so anything added there invalidates the whole repository's cache. Check a new entry genuinely affects every task rather than one.

### General

- Secrets never appear in `vars` in a committed wrangler config. They are set with `wrangler secret put` and read from `env`. Local values belong in `.dev.vars` (or `.env`, but not both: `.dev.vars` wins and excludes `.env` entirely), which must be gitignored; per-environment variants are `.dev.vars.<environment-name>`. A `secrets.required` list turns a missing secret into a deploy failure rather than a runtime one.
- CPU time counts executing code only, not time awaiting `fetch`, D1, or KV, so an added `await` is not itself a CPU-limit risk and a review comment claiming otherwise is wrong. Memory is 128 MB on both plans, so a large request or response body should be streamed rather than buffered.
