## TypeScript

Detected from a `tsconfig.json`, with no framework, runtime, or ORM required. This is deliberately framework-agnostic groundwork: it covers the language-level pitfalls that hold whatever the project is built on, so the more specific TypeScript fragments loaded alongside it build on this rather than restating it.

**Read `tsconfig.json` before applying any of this.** Several checks below only exist when a particular flag is on, and the most useful one is not part of `strict`. Look rather than assume. Formatting and import order belong to Prettier and ESLint; do not repeat them, and never suggest a suppression comment to get past a rule.

### Escape hatches from the type system

- `as` is erased at emit: a wrong assertion produces no runtime check and no exception, and silently propagates a lie into every downstream consumer. Treat each one in a diff as a claim the author is making, not one the compiler verified.
- `as unknown as T` exists specifically to defeat the rule that a direct assertion must be between sufficiently overlapping types. The compiler has already refused the single-step cast; the double cast overrides that refusal and needs a justification or a real type guard.
- `as` on an object literal also bypasses excess-property checking, so `{ width: 100, opacity: 0.5 } as SquareConfig` compiles with `opacity` undeclared. An assertion added to a literal purely to make it compile is often the signal a field name was misspelled. `satisfies` (TS 4.9+) is almost always what was wanted: it validates the literal against the type, excess-property checks included, while leaving the expression its own narrower inferred type.
- `any` disables checking for everything reached through it, not just what it annotates; `unknown` plus narrowing keeps the checks. A non-null `!` is the same unchecked claim as `as`, deferring a real absence to a runtime failure elsewhere.
- Prefer `@ts-expect-error` to `@ts-ignore`: it reports `Unused '@ts-expect-error' directive` once the line stops erroring, so it removes itself rather than outliving the problem.

### Type guards that lie

- A hand-written predicate (`function isFish(pet: Pet): pet is Fish`) is not checked against its own body. TypeScript's own 5.5 notes put it bluntly: the compiler "will not check whether it would infer the same type predicate", and explicit predicates "are no safer than a type assertion". One that checks the wrong property, checks a property present on both members, or returns `true` on the wrong branch compiles cleanly and corrupts narrowing at every call site. The question is whether the runtime check actually implies the claim, because compiling proves nothing here.
- TS 5.5 infers predicates for simple functions (no explicit return type, a single return, no mutation of the parameter), so `arr.filter(x => x !== undefined)` narrows `(T | undefined)[]` to `T[]`. Annotating that same callback `(x): boolean` switches the inference off and silently hands back the widened array, so a `boolean` return annotation on a filter callback is worth questioning. A truthiness check does not, for unions including primitives, because falsy does not prove nullish: over `(number | undefined)[]` or `(string | undefined)[]`, `filter(Boolean)` both leaves the array widened and discards legitimate `0` and `""`.

### Structural typing

- Object types are not sealed: a value typed `{ a: string }` can carry further properties at runtime, since compatibility only requires the declared members. Much surprising behaviour follows from this one fact.
- Following directly from it, `Object.keys(obj)` is typed `string[]` rather than `(keyof T)[]` deliberately, so the common `Object.keys(obj) as (keyof T)[]` is unsound rather than merely verbose: it asserts the runtime key set is exactly `T`'s declared keys, which the language does not guarantee.
- Excess-property checking is a freshness check firing only on a literal assigned or passed directly. The same extra property is accepted once the value goes through an intermediate variable, comes back from a function call, or arrives via a spread. Note the bypass is about where the value has been, not about crossing a function boundary: a literal returned directly against a declared return type is still checked. A literal that stopped erroring because someone extracted it to a local is worth asking about: that is a well-known, usually unintentional way to silence a real typo.
- Structurally identical types are interchangeable with no declared relationship, so bare aliases used as if nominal (`type UserId = string` alongside `type OrderId = string`) do not stop the two being swapped at a call site. Flag code relying on them for safety with no branding applied.

### Compiler flags worth checking before assuming

- **`noUncheckedIndexedAccess` is not implied by `strict: true`.** Check for it explicitly. When on, every read through an index signature yields `T | undefined`, including a `Record<string, T>` lookup, since `Record` is a mapped type over an index signature, so a `record[id].bar` compiling without a guard means the flag is off and that lookup is a latent `undefined`. Prefer an explicit check handling the absence over a `??` sentinel, which turns a missing value into a plausible-looking wrong one. Named properties declared on the interface are unaffected; only access resolving through the index signature.
- The same flag covers a computed array index (`arr[i]`), easy to miss because an array does not look like it has an index signature, which is why `for...of` and `.forEach` are preferred to a counting loop. With the flag on, a manual indexed loop has to bind the element and check it, so one that reads `arr[i]` straight through and still compiles is either using `!` to work around real safety or running without the flag. A tuple indexed by an in-bounds literal stays exempt, so that is not a finding.
- **`strictFunctionTypes`** is on under `strict` but individually disableable, and with it off the codebase accepts unsound callback-parameter substitutions a reviewer might assume were caught. Its contravariant checking applies to function-typed _properties_ (`compare: (a: T, b: T) => number`) but explicitly not to _method_ syntax (`compare(a: T, b: T): number`), which stays bivariant so `Array<T>` and friends stay useful. Rewriting a property-style callback as a method, or the reverse, therefore silently changes how strictly it is checked with no behavioural change to the code.
- Arrays are covariant, which is unsound: a `Dog[]` is assignable to `Animal[]`, after which something can push a `Cat` into the original array. `readonly T[]` does not remove the covariance but removes the mutating methods that make it dangerous, and assignability runs one way only: mutable to readonly, never the reverse. What matters is whether a function taking a widened array type ever writes into it.

### Discriminated unions and exhaustiveness

- Only the `never` assignment makes a switch exhaustive-_checked_: a `default` assigning the narrowed remainder to `const _exhaustive: never = value` becomes a compile error the moment a member is added and a case missed. A `default` that returns a fallback, logs, or does nothing compiles forever and silently swallows every member added later. Its presence reads as "handled" while enforcing nothing, so check which of the two it is rather than that one exists.

### Enums

- A numeric enum emits a reverse mapping (`Enum[Enum.A] === "A"`), so the compiled object holds both directions and `Object.keys`/`Object.values` return twice as many entries as it has members. Any code iterating an enum's own keys or values expecting only the named members is a bug. String enums emit no reverse mapping, so this is a numeric-enum trap specifically.
- `const enum` is erased and inlined at every use site _by default_, leaving no runtime object, but do not assume that from the declaration alone: under `preserveConstEnums`, and under `isolatedModules`, a locally declared `const enum` emits a real enum object after all. What `isolatedModules` actually rejects is an _ambient_ `const enum`, one declared in a `.d.ts`, because inlining that needs cross-file type information (`Cannot access ambient const enums when 'isolatedModules' is enabled`). Where inlining does happen it carries a version-skew hazard: a value inlined out of a dependency's `.d.ts` is never re-read at runtime, so it can diverge from whatever that dependency actually ships. In anything published or consumed elsewhere, prefer a plain enum.

### Promises and async

- A floating promise, meaning a Promise-valued expression statement not awaited, returned, given a `.then` with a rejection handler, given a `.catch`, or `void`-prefixed, has its rejection observable nowhere. In Node an unhandled rejection has been raised as an uncaught exception by default since v15, so it can take the process down rather than merely logging; in a browser or a Worker it only reaches an `unhandledrejection` handler, which is why identical code can be harmless in one target and fatal in another.
- `void somePromise()` is the accepted idiom for deliberate fire-and-forget, but only silences the lint: it does not handle the rejection or change runtime behaviour. If the failure matters, it still needs a `.catch`.
- `items.map(async (i) => process(i))` returns `Promise<Result>[]`, not `Promise<Result[]>`. An `async` function returning it is inferred `Promise<Promise<Result>[]>` with nothing reported, because the await-unwrapping reaches the top level only and not inside the array; the bug surfaces at runtime as pending Promise objects where values were expected. Flag any `.map(async ...)` whose result is not handed straight to `Promise.all`/`allSettled` or otherwise awaited element by element.
- `new Promise(async (resolve, reject) => { ... })` loses errors: the constructor discards the executor's own promise, so _any_ throw in it, not only one after the first `await`, becomes an unhandled rejection on that discarded promise instead of rejecting the one being constructed. A plain executor's synchronous throw is caught by the constructor and does reject it, so the `async` keyword is precisely what removes that safety. The fix is almost always to drop the constructor.
- `Promise.all` rejects on the first rejection but does **not** cancel the others, which keep running unobserved, and because it marks every input handled the instant it is called, every rejection after the first is swallowed and never reaches an unhandled-rejection handler. Over independent side-effecting calls, where one failure should not hide the other outcomes, `Promise.allSettled` is what was wanted.
- A sequential `for (const x of xs) { await f(x) }` costs the sum of each call's latency where `await Promise.all(xs.map(f))` costs roughly the maximum. Flag it only where the iterations are provably independent: no shared mutable state, no ordering requirement.
- The inverse mistake is as real. `Promise.all` orders the _result array_ by input; it says nothing about the order operations take effect. Parallelising writes whose correctness depends on a prior write's result (a foreign key needing the previous row's generated id, a rename and a move on one resource) races them. Treat "we parallelised these for speed" as a claim to check whenever the writes touch the same row, resource, or aggregate.
- `const results = [await p1, await p2]`, over already-running independently-rejectable promises, can produce an unhandled rejection even inside a `try`/`catch`, because `p2` can reject before anything is attached to observe it. One `Promise.all` or `Promise.allSettled` call fixes it by subscribing to both immediately.
- Do not flag a `throw` inside an `async` body on these grounds: it rejects the returned promise exactly as a `throw` in a `.then` callback does, and is caught identically by the next `.catch` or enclosing `try`/`catch`.

### Modules and interop

- `require()` of an ES module is a recent Node capability, unflagged only from v20.19, v22.12 and v23, so on an older engine it throws `ERR_REQUIRE_ESM` whatever the module contains; check the project's declared `engines` before treating one as fine. Where it is available it still needs the whole imported graph to be synchronous: top-level `await` anywhere in it throws `ERR_REQUIRE_ASYNC_MODULE`. Dynamic `import()` works from both CommonJS and ESM on every version, is always asynchronous, and can load a module with top-level `await`.
- Importing CommonJS from ESM makes `module.exports` the default export, with named exports synthesised by best-effort static analysis of the source. That detection is a snapshot taken at load: later mutation of `module.exports` is not reflected in the binding, so code relying on a CommonJS export being reassigned after load is a finding.
- `verbatimModuleSyntax` makes emit follow the syntax actually written instead of rewriting it to suit `module`, dropping only type-only imports. Under `module: commonjs` that turns every ESM `import`/`export` in a file into a compile error, since each would otherwise have been silently rewritten to a `require()`; CommonJS has to be written `import x = require(...)` and `export =` there. Dynamic `import()` is rejected under `module: commonjs` too, because it is downlevelled as well, but is left alone under `node16`/`nodenext`, where it survives into CommonJS output intact.

### Circular imports and barrel files

- In CommonJS a module requiring a still-executing module receives its _partial_ `exports` as of that moment. In ESM, imports are live bindings with temporal-dead-zone semantics: reading one before the exporting module has run the corresponding statement throws `ReferenceError: Cannot access 'X' before initialization`, while the same read after top-level code finishes (inside a callback, say) succeeds. Function declarations are the exception, hoisted and initialised before any module body runs, so a cycle whose modules only call each other's functions works while one reading a `const` at module scope throws. An ESM cycle therefore fails or works depending on _what_ is read and _when_, not on whether the cycle exists, which is how one survives review and CI and then breaks on an unrelated import-order change.
- A barrel (`index.ts` re-exporting a folder) is the usual accidental route into that error, when a file imports from its own folder's barrel and the barrel re-exports that file; editor auto-import introduces these without anyone deciding to. Within a package, import directly from the sibling module and reserve the barrel for the external surface. An `import/no-cycle` rule catches these before they become a runtime `ReferenceError`.
- A barrel also blocks tree-shaking unless the bundler can prove it and every intermediate re-export is side-effect-free, via `sideEffects` in `package.json`. Watch for the opposite error in a `package.json` diff: declaring `sideEffects: false` on a package that genuinely has side effects (CSS imports, polyfills, prototype patches) silently drops code that needed to run.
- Outside a bundler, in a dev server, `tsc`, or a test runner, a barrel forces the whole re-exported graph to load even for one symbol, because modules load in full to preserve execution order. That is the usual explanation for a test suite or dev server disproportionately slow for the code actually under test.
